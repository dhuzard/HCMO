# BEATBox — HCMO coverage example (synthetic outputs)

- **Project:** Open-BeatBox — **BE**havioural and **A**u**T**onomous operant **Box**
- **Type:** open-source (hardware CERN OHL-S v2, firmware GPLv3, software AGPLv3)
- **Modality:** autonomous home-cage operant conditioning with **touch screens**,
  nose poke, pellet feeder, IR barriers and programmable lighting
- **Status:** active; real builds and assembly documentation exist, several
  details (cost benchmarks, protocol templates, **data output format**) are
  still listed as under validation in the project manual
- **Data provenance:** **synthetic.** The
  [`beatbox_can_event_log.csv`](datasets/mock/beatbox_can_event_log.csv) rows are
  the **documented inter-module CAN messages** (module IDs, message names,
  payloads, and the 11-bit identifier computed with the published formula), so
  that layer is faithful to the manual. The
  [`beatbox_trials.csv`](datasets/mock/beatbox_trials.csv) table is **designed
  for this evaluation**: BEATBox's manual lists "data output format" as planned
  content, so no vendor trial export exists to imitate. Both are generated by
  [`generate_hcmo_instance.py`](generate_hcmo_instance.py) with a fixed seed.

## Overview

BEATBox lets mice run cognitive tasks inside their home cage over days and
weeks, instead of in short experimenter-driven sessions. A Raspberry Pi main
controller drives peripheral modules over a CAN bus: a feeder, a nose-poke
module, **left and right touch screens**, a lighting module (white / red /
infrared duty cycles) and IR barriers. The animal initiates each trial itself,
so trial rate and accuracy carry motivational and circadian information that a
fixed-session protocol cannot show.

## Scenario in this example

| | |
|---|---|
| Housing | **single-housed**, one mouse per box, four boxes |
| Strains | C57BL/6J, BALB/cJ, DBA/2J, 129S1/SvImJ (one per box, males and females) |
| Task | two-choice **visual discrimination** on the touch screens, nose-poke initiated, one pellet per correct touch, rewarded side reversed after criterion |
| Session | 6 h, 17:00–23:00, spanning the light→dark transition (dark from 19:00 via the lighting module) |
| Volume | 275 self-initiated trials, 1,737 CAN messages |

Per-strain accuracy differs in the mock (C57BL/6J highest, DBA/2J lowest) and
every animal runs more trials with shorter latencies in the dark phase, so the
cross-system competency questions have something to find.

## Hardware modules (from the manual)

| Module | CAN ID | Role | Modelled as |
|---|---|---|---|
| MAIN (Raspberry Pi shield `BB_RPi_shield_V1.1`) | `0x1` | controller | `hcm-tech:Hardware` + `hasProtocol` |
| FEEDER (`BB_Feeder_main_V1.1`) | `0x2` | pellet delivery | `hcm-tech:Actuator` |
| NOSEPOKE | `0x3` | trial initiation | `hcm-tech:Sensor` |
| SCREEN_LEFT / SCREEN_RIGHT | `0x4` / `0x5` | stimulus + touch | `hcm-tech:Actuator` (display) + `hcm-tech:Sensor` (touch) |
| LIGHTING (`BP_Lighting_V1.1`) | `0x6` | white/red/IR schedule | `hcm-tech:Actuator` |
| IR_BARRIER (`BB_Feeder_IRBarrier_V1.1`) | `0x7` | pellet collection | `hcm-tech:Sensor` |

## Data output

- **`beatbox_can_event_log.csv`** — `timestamp, box, module, message, payload,
  can_id, prio`. Message names and payloads follow the manual's protocol tables
  (`BEAM_EVENT`, `DISPLAY_PATTERN`, `TOUCH_EVENT`, `REQUEST_REWARD`,
  `REWARD_DELIVERED`, `BARRIER_EVENT`, `SET_DUTY`), and `can_id` is computed as
  `(PRIO << 8) | (MODULE << 4) | (TYPE << 2) | CMD`.
- **`beatbox_trials.csv`** — one row per trial with the animal, strain, task,
  S+ side, patterns, response side, correctness, response and collection
  latencies, and the light phase. **Designed, not vendor-published.**
- **Timestamps:** ISO 8601 with an explicit UTC+02:00 offset.

## HCMO mapping

The complete table is [`hcmo-mapping.tsv`](hcmo-mapping.tsv) (33 concepts).
Highlights:

- **Fits HCMO:** the box, enrichment, single housing, every hardware module as
  a sensor / actuator / controller with its PCB identifier, the GUI as software,
  both files as time series, the collection latency as a quantity observation,
  and the lighting schedule as an `hcm-env:LightCycle`.
- **Generic pattern (partial):** correctness is an `hcm-obs:CategoricalResult`
  and the latencies are `hcm-obs:QuantityValue`s on plain `sosa:Observation`s,
  because HCMO 0.3.0 has **no operant or cognitive observation subtype**. The
  task, its schedule and its stimulus parameters live as free text on a reused
  `sosa:Procedure`.
- **Not covered:** the trial as an entity (its observations only share an
  interval), the session/study-stage, stimulus-presentation and reward-delivery
  as actuation events, and the CAN addressing layer itself.

**Gaps exposed:** cognitive and operant work needs a task/trial/session
vocabulary that HCMO does not yet have — this is the clearest single gap of all
six systems mapped so far, and it applies equally to FED3.
