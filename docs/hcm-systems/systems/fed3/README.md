# FED3 (Feeding Experimentation Device 3) — HCMO coverage example (synthetic log)

- **Authors:** Matikainen-Ankney et al. 2021 (Kravitz lab), open-source hardware
- **Type:** open-source / DIY
- **Modality:** operant nose-poke + pellet feeding inside a standard home cage
- **Status:** active (FED3 library ≥ 1.16)
- **Chapter reference:** Huzard et al. 2026, open-source systems (FED3)
- **Data provenance:** **synthetic, schema-faithful.** The log
  `datasets/mock/FED001_060226_00.CSV` is generated by
  [`generate_hcmo_instance.py`](generate_hcmo_instance.py) with a fixed seed and
  follows the FED3 library column layout; the events are not recorded data.

## Overview

FED3 is a battery-powered, Arduino-compatible device placed inside a standard
cage. Two nose-poke ports (infrared photointerrupters) register pokes, a stepper
motor dispenses 20-mg pellets into a well monitored by a third photointerrupter,
and every event is appended to a CSV file on an SD card. Sessions run operant
schedules such as FR1 (one active poke = one pellet), progressive ratio, or free
feeding.

## Monitored entities

- **Species:** mouse (rat variants exist)
- **Housing:** single in the mock (group use possible with RFID add-ons)
- **Enclosure:** standard mouse shoebox cage; dimensions are **assumed** for the
  synthetic profile (19.5 × 32.5 × 13.0 cm) and flagged in the graph

## Sensors & actuators

| Component | Transduces | Modelled as |
|---|---|---|
| left / right nose-poke photointerrupters | poke onset and duration | `hcm-tech:Sensor` (`installedIn` cage) |
| pellet-well photointerrupter | pellet presence → retrieval latency | `hcm-tech:Sensor` |
| pellet dispenser stepper motor | pellet delivery | `hcm-tech:Actuator` |
| FED3 device (Feather M0 Adalogger) | logging, schedule control | `hcm-tech:Hardware` with `hasFirmware` = Library_Version |

## Data output

One CSV row per event with the FED3 library columns:

```
MM:DD:YYYY hh:mm:ss, Library_Version, Session_type, Device_Number, Battery_Voltage,
Motor_Turns, FR, Event, Active_Poke, Left_Poke_Count, Right_Poke_Count,
Pellet_Count, Block_Pellet_Count, Retrieval_Time, InterPellet_Interval, Poke_Time
```

- **Event:** `Left`, `Right` (pokes) or `Pellet`; `Retrieval_Time` (s) is set on
  pellet rows, `Poke_Time` (s) on poke rows.
- **Mock session:** FR1, active poke Left, 3 h from 2026-06-02 18:30 (UTC+02:00),
  208 rows (109 pokes, 99 pellets), spanning the light→dark transition (dark
  from 19:00).
- **Timestamps:** device clock, local time without offset; the graph adds
  UTC+02:00.

## HCMO mapping

The complete mapping is [`hcmo-mapping.tsv`](hcmo-mapping.tsv) (25 concepts).
Highlights:

- **Fits HCMO:** device, sensors, actuator, firmware and log file map to the
  `tech` module; `Retrieval_Time` becomes a `hcm-obs:QuantityValue` result (s)
  and also the phenomenon interval of the pellet observation; `Poke_Time` becomes
  the duration of the poke observation's `time:Interval`.
- **Generic pattern (partial):** pokes are `sosa:Observation`s with
  `hcm-obs:CategoricalResult` (left/right nose-poke); HCMO has no operant-event
  subtype. The FR schedule and active poke are a reused `sosa:Procedure`.
- **Not covered:** battery voltage, motor turns (device/actuator telemetry) and
  block pellet counts; cumulative counters are derivable and not materialised.

**Gaps exposed:** event-based (irregular) data need an instant or a
zero-length interval; HCMO's bounded-interval shapes force a duration, which
`Poke_Time`/`Retrieval_Time` happen to provide. There is no HCMO property for a
device identifier (`dcterms:identifier` reused) nor for schedule parameters.
